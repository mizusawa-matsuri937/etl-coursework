# 任务 5 规格（人物姓名归一与消歧）

状态：2026-10-29 编写计划；同日用户确认角色范围、主演依据、无外部 ID 人物的归并方式与 IMDb 人员的用法（H01–H04）。2026-10-30 用户要求加强没有 IMDb 关联作品的跨作品人物匹配：新增作品年表反查（R14–R16）、合作者佐证迭代（R21）、只记录的名字稀有度与发行商特征（R22）、按影响排序的待复核队列（R30），规则与 AC 重新编号，评价增加一层（H13–H15）。2026-10-30 用户审批通过计划，其余假设按建议执行。同日 T5-07 在正式库经 Airflow 全量运行（规则 `t5r1`，人物映射版本 `pmap0001`），AC14、AC16、AC17 通过；AC15 等用户标注。设计见 [design](design.md)，执行顺序见 [tasks](tasks.md)，完成情况见 [checklist](checklist.md)。

## 目标

为任务 4 作品所涉及的页面人物生成稳定的 `person_id`，保存原始姓名、规范姓名、别名、外部人物 ID（IMDb `nconst`）与匹配证据。外部 ID 有两条确认途径：在商品关联的 IMDb 作品的演职员里按“同作品、同角色、姓名兼容”确认；对没有 IMDb 关联的作品，反查已在别处核实的同名人物的 IMDb 作品年表，有同名作品时确认。仍没有外部 ID 时，姓名相同不合并，跨作品只在有共同合作者佐证时合并（佐证随合并结果迭代计算），其余保留为多个实体并标为待复核。通过 MoviePerson 保存导演、主演、演员三种角色，保留来源角色与署名顺序。最后用 120 对用户标注的独立样本报告人物自动合并的 Precision、Recall、F1，并展示至少 5 组别名合并与 5 组同名或近似名不合并的实例。

## 范围

- 包含：任务 4 参与匹配的电影类与合集商品页面上的导演与演员署名（署名行与详情要点）；人物提及的抽取、姓名规范化与多种比较键；在关联 IMDb 作品的演职员中确认外部人物 ID；对没有 IMDb 关联的作品反查已核实人物的 IMDb 作品年表；同作品与跨作品的人物候选、三档判定、合作者佐证迭代、聚类一致性检查；名字稀有度与发行商特征的记录；稳定 `person_id`、规范姓名、别名、外部 ID、人物映射版本、人工纠正与按影响排序的待复核队列；MoviePerson 的导演、主演、演员关系与来源；分批恢复、幂等与 Airflow 编排；统计报告、实例与两个人物查询；评价样本与簇抽查的导出、标注导入和指标计算；任务 4 升级线索的记录。
- 不包含：编剧、制片、Contributor 等其他角色的关系（只计数）；剧集、演唱会等非参与匹配商品的人物；IMDb 中页面没有列出的演职员的 MoviePerson（页面与 IMDb 演员表的并集与冲突留给任务 7）；升级任务 4 的匹配规则（`t4r3`）或修改任务 4 的作品归属；上映信息（任务 6）；评论去重（任务 8）；完整的字段级血缘（任务 9）；另装 IMDb 编剧、制片数据；在全量 205 万个 IMDb 人物里按姓名搜索；重新请求页面；用 AI 或机器学习模型判定是否同一人。
- 约束：不修改任务 1–4 的 spec、表结构、数据与测试，只读 `public`、`task2`、`task3`、`task4`、`imdb`；新表放在 schema `task5`；沿用 Python + PostgreSQL + Airflow + Docker Compose；测试不访问外网、只写 `etl_test`；IMDb 文件、导出与评价表不提交到仓库。
- 依据：[作业说明](../../../作业/数据存储与管理_ETL作业说明.docx)的任务 5（`person_id`、原始与规范姓名、别名、外部 ID、匹配证据、中间名缩写音译、参演作品职业年代等证据、可优先利用已核实的外部人物标识、姓名相同不代表同一人、待复核、实例、MoviePerson、合并准确性）、第五部分（导演与主演经人物实体关联、来源角色与排序、主演判定依据）、第八部分（Person、PersonAlias、MoviePerson、MergeDecision、FieldAssertion、SourceRecord，可重复运行与恢复）、第九部分（输入 `person_id` 的血缘查询）、第十部分（合并前后人物数量、实体匹配评价、簇抽查、查询某导演的作品及来源）；[任务 4 交接文档](../handoffs/2026-10-29-task4-to-task5.md)。

## 规则

“作业要求”来自任务书，“用户选择”来自 2026-10-30 及以前的对话，“工程默认”是本轮实现基线。R01–R05 为输入与人物提及，R06–R09 为姓名规范化，R10–R16 为外部人物 ID，R17–R25 为人物归并，R26–R30 为标识、别名、版本与复核，R31–R34 为 MoviePerson，R35–R39 为评价与实例，R40–R47 为统计、查询与工程。

- R01 [作业要求]：输入限定为一个抽取、一个任务 4 映射版本和一个 IMDb 快照；默认为正式库抽取 `f1e8b845…`、映射版本 `map0002`（规则 `t4r2`）、快照 `imdb_2026-10-29`，任务 3 解析版本取该映射版本所用的 `t3p1`；所有读取都带这些条件。
- R02 [工程默认]：只处理任务 4 中 `match_scope = matched` 的商品（电影类与合集）；其他商品的人物不抽取。
- R03 [用户选择]：只为导演、演员建立人物提及；编剧、制片、Contributor 等署名只按标签计数进报告，不建提及。
- R04 [用户选择]：导演取署名行 Director，没有署名行时取详情要点 Director；演员取署名行 Actor 与详情要点 Actors 的全部名字。每个名字一条人物提及，保留区域、序号、列表内位置、原始标签与原值，指回 `task3.page_field`；与任务 4 断言对应的提及同时记 `assertion_id`。
- R05 [作业要求]：详情要点按逗号拆分；无法确定“姓, 名”边界的串（任务 4 的 `name_ambiguous` 规则）其提及标为 `ambiguous`，不参与归并；占位署名（Various 等）标为 `placeholder`，不建人物；两类都计数报告。
- R06 [作业要求]：原始姓名原样保留；规范化（`t5n1`）先把只含一个逗号的“姓, 名”倒序（后缀如 Jr. 不倒序），再分出引号昵称、括号消歧段（如 “(III)”）、后缀与称谓，均另存不丢弃。
- R07 [作业要求]：每条提及生成严格键（去重音、大小写折叠、去标点）、宽松键（去掉中间的单字母缩写）、词集键（不计词序）、姓氏键与“首字母 + 姓”键；含替换字符 U+FFFD 的姓名标为 `encoding_damaged`。
- R08 [作业要求]：宽松键、词集键、首字母键、去中间名、统一大小写与编辑距离只用于生成候选和判断姓名兼容，不能单独作为合并依据。
- R09 [作业要求]：IMDb 一侧对 `primary_name` 用同一规范化函数；每个 IMDb 人物保留 `nconst`、出生与去世年份、职业及源记录（快照、文件、行号）。
- R10 [用户选择]：外部人物 ID 的第一条途径是在商品关联的 IMDb 作品的演职员中查找：电影类商品取 `edition` 关系作品的 `tconst`，合集取各 `contains` 成员作品的 `tconst`；导演对 `imdb.title_director`，演员对 `imdb.title_principal` 的 actor/actress；不在全量 IMDb 人物里按姓名搜索。
- R11 [工程默认]：提及与演职员的姓名兼容分四级：X1 严格键相同；X2 词集键相同；X3 首末词兼容且只差中间缩写、中间名、昵称或后缀；X4 近似（替换字符通配，或编辑距离 ≤2 且首字母相同）。
- R12 [工程默认]：同一作品、同一角色类别中恰好一位演职员达到 X1–X3、且没有其他达到 X1–X4 的演职员时，自动关联其 `nconst`；X4、多人兼容、只在另一角色类别兼容时为复核；没有兼容者不关联。
- R13 [作业要求]：每个外部 ID 判定写一条决策：提及、候选 `nconst`、途径、作品 `tconst`、兼容等级、角色类别、证据源记录、规则版本、判定档、置信度；未采用的候选同样保存。
- R14 [用户选择]：外部人物 ID 的第二条途径是作品年表反查：提及所在作品没有 IMDb 关联（或合集提及未归属到成员作品）时，若同严格键、同角色类别的人物已经按 R12 自动关联到 `nconst` N，且 N 在 IMDb 中同角色的作品里恰有一部的标题键（含别名，取任务 4 的 IMDb 标题键）等于该商品或某合集成员的标题键，则自动关联到 N。
- R15 [作业要求]：作品年表反查只使用已按 R12 核实的 `nconst`，不用全量 IMDb 姓名；年表里有多部同名作品、或多个同名的已核实人物都满足时为复核；该作品的 IMDb 年份与商品标题年份相差超过 1 年，或存在 R20 的硬冲突时不自动关联；IMDb 只有主要演职员，没有命中不算反证。
- R16 [工程默认]：同一商品有至少两条提及经作品年表反查指向同一 IMDb 作品时，记为任务 4 升级线索（商品、`tconst`、提及与证据），只计数报告，不改任务 4 的数据与该商品的作品归属。
- R17 [作业要求]：姓名相同不代表同一人：没有外部 ID 时，不同作品中严格键相同的提及不能只凭姓名合并；名字缩写相同更不能合并。
- R18 [用户选择]：同一 `movie_id` 内，严格键相同的提及（不分角色），或同一角色类别内词集键相同的提及，归为同一人物；组内有提及已自动关联 `nconst` 时整组归入该人物。
- R19 [用户选择]：跨作品自动合并只有两条途径：两边自动关联到同一 `nconst`（经 R12 或 R14）；或者严格键相同、角色类别相同、两部作品有共同合作者（见 design），且没有 R20 冲突。其余跨作品同名或兼容姓名对判为复核或不合并。
- R20 [作业要求]：硬冲突时不得合并：两边关联到不同 `nconst`；两边带不同的括号消歧段；或一边的 IMDb 出生、去世年份与另一边作品的年份不相容（阈值见 design）。
- R21 [用户选择]：合作者佐证迭代计算：每一轮合并后，把新获得外部 ID 或新合成的人物当作已核实的合作者，重新计算共同合作者，直到某一轮没有新的自动合并；每轮做一致性检查；处理顺序固定，同一输入得到同一结果与同一组 `person_id`；迭代轮数与每轮新增的合并数写入报告。
- R22 [用户选择]：名字稀有度（该严格键在页面出现的作品数、IMDb 中同严格键的人数）与商品层信号（两边商品的发行商或发行系列相同）作为特征记录；是否参与判定由规则版本的开关决定（`t5r1` 默认关闭）。打开时，稀有度只能在“同角色、至少一位同名合作者”时把复核升为自动，发行商相同最多给合作者分加 1；两者都不能单独作为合并依据。
- R23 [作业要求]：聚类一致性：一个人物最多关联一个 `nconst`；某条自动边会把两个不同 `nconst` 或互相冲突的提及连到一起时不执行该边，改为复核并写一致性记录；复核与不合并的边不连接人物簇。
- R24 [作业要求]：无法确认时保留多个实体：没有外部 ID 且有复核候选的人物状态为 `review_pending`，有外部 ID 的人物记待复核候选数，两者都能列出候选；待复核率单独报告。
- R25 [作业要求]：每个跨作品候选写一条合并决策：候选双方、生成器、特征与证据（含 R22 的特征，即使未参与判定）、得分、置信度、阈值、规则版本、迭代轮次、运行与判定者（`system` 或 `human`）；未采用的候选同样保存。
- R26 [作业要求]：`person_id` 由系统生成，不含 `nconst` 或姓名原文，生成后不复用；按锚点登记（有外部 ID 的以 `nconst` 为锚点，否则以簇内最小提及键为锚点），同一输入与规则版本重跑得到同一组 `person_id`。
- R27 [作业要求]：Person 保存规范姓名、规范姓名来源、状态与外部 ID；规范姓名在有外部 ID 时取 IMDb `primary_name`，否则取提及中最常见的规范写法（并列取字典序最小）。
- R28 [作业要求]：PersonAlias 为每个人物的每种不同原始写法一行，记别名类型（如倒序、大小写、重音、中间缩写、中间名、昵称、IMDb 主名）、出现次数与对应提及；IMDb `primary_name` 作为来源为 IMDb 的别名。
- R29 [作业要求]：每次生成人物映射形成一个人物映射版本，记录提及、人物、外部 ID 覆盖与待复核数量；支持导入人工决策（`must_link`、`cannot_link`、`detach`）生成新版本，人工优先，与年代或消歧段冲突矛盾时仍执行但标出，要求合并两个不同 `nconst` 的决策在导入时拒绝；旧版本可以查询。
- R30 [用户选择]：待复核队列按“采纳后能连起的作品数”降序导出（并列按候选 ID），每行带双方证据与可直接填写的 `must_link`/`cannot_link` 列，填好后用 R29 的导入命令导入。
- R31 [作业要求]：MoviePerson 以（人物映射版本，`movie_id`，`person_id`，角色）为主键，角色取 `director`、`starring`、`cast`；同一人在同一作品中可以有多个角色。
- R32 [用户选择]：`starring` 只来自页面署名行的 Actor；`cast` 为署名行与详情要点演员的并集；IMDb 的 `ordering` 只作为证据保存，不作为主演依据；页面没有列出的 IMDb 演职员不建关系。
- R33 [作业要求]：保留来源角色（原始标签与区域）与署名顺序：`director`、`starring` 的署名顺序取署名行内同角色的序号；详情要点名单按字母排序，署名顺序为 NULL，只保存列表位置；多个商品版本顺序不一致时取最小值并标出。
- R34 [作业要求]：每条 MoviePerson 关联它的全部来源提及；电影类商品经 `edition` 关系归到作品；合集页面的提及只有在经 R12 关联到某个成员作品的 IMDb 演职员，或经 R14 命中某个成员的标题键时，才经 `contains` 归到该成员作品，其余记为 `unattributed`，不建关系。
- R35 [作业要求]：规则开发样本与评价样本分开：按 `md5(姓氏键)` 排序，前 20% 的姓氏键冻结为开发池，只用于调整阈值与决定 R22 开关；评价对的两边姓氏键都不在开发池。
- R36 [用户选择]：评价样本为 120 对来自不同作品的提及，分层覆盖别名合并、作品年表反查、合作者佐证、同名不同人、名字缩写、近似名与无外部 ID 的同名（层次见 design）；导出表带双方原名、作品、角色、年份、IMDb 与页面地址，不显示系统判定；AI 只在草稿副本里给出预标注，用户逐条审核后以用户为标注人导入；“不确定”不计入指标，单独报告数量。
- R37 [作业要求]：用已标注样本计算人物自动合并的 Precision、Recall、F1（预测同一指双方属于同一 `person_id` 且只来自系统判定），并按途径与层报告，列出误合并与漏合并实例；分母为零记为“无定义”；人工复核覆盖率与待复核率单独报告；报告注明指标只代表评价样本。
- R38 [作业要求]：从评价池随机抽 20 个跨至少两部作品的人物，由用户检查是否混入不同的人，用于发现传递合并错误，结果单独报告。
- R39 [作业要求]：报告列出至少 5 组人物别名合并与至少 5 组同名或近似名不合并的实例，每组附原始署名、作品、外部 ID 或冲突证据与可定位的源记录；用户标注过的实例注明结论。
- R40 [作业要求]：每次运行导出报告到 `outputs/task5/<抽取>/<人物映射版本>/<run_key>/` 并记录文件哈希：合并前后数量（提及、不同原始写法、不同严格键 → 人物），按途径（作品演职员、作品年表、合作者佐证）的外部 ID 与合并数（第三方来源分开），迭代轮数与每轮新增，人物状态与判定档分布，R22 特征打开时会改变判定的候选数，MoviePerson 按角色与来源计数，多角色人物数，`ambiguous`、`placeholder`、`unattributed` 提及数，其他角色署名数，任务 4 升级线索数；导出不含评论正文与整页 HTML。
- R41 [作业要求]：提供两个只读查询：输入 `person_id` 返回原始署名、别名、归并决策链与参与作品；输入导演姓名返回匹配的人物、其作品及来源（同名的多个人物分别列出）。
- R42 [作业要求]：同一输入、同一规则版本、同一组人工决策重跑时，不新增也不修改目标行，只记一条 `reused` 审计。
- R43 [作业要求]：分批处理：提及与第一条途径的外部 ID 判定按商品分批，每批与批次标记在同一事务提交；中断后重跑只处理未完成的批次；同一抽取同时只允许一个运行。
- R44 [作业要求]：规则或输入（任务 4 映射版本、IMDb 快照、人工决策）变化时生成新的人物映射版本，只重算受影响的阶段，并能列出两个版本之间 `person_id` 变化的提及与原因。
- R45 [作业要求]：由 Airflow DAG `amazon_movies_task5_person`（检查输入 → 人物提及 → 外部 ID → 归并与人物 → MoviePerson → 核对 → 收尾报告 → 门禁）执行；确定性错误不重试，暂时错误最多重试 2 次，收尾成功不掩盖上游失败。
- R46 [工程默认]：表结构为迁移 `401`（schema `task5`）；每次运行记录规范化版本、规则版本、任务 4 映射版本、IMDb 快照、人工决策集与运行审计；不写任务 1–4 的任何表。
